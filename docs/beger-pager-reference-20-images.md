# Beger — مرجع الأفكار والقرارات من 20 صورة

**النوع:** مرجع منتج وتنفيذ (ليس مواصفات مكتملة ولا إعلاناً عن ميزات منشورة)  
**المصدر:** مجموعتا الصور المرجعية اللتان أرسلهما المستخدم في محادثة Beger بتاريخ 2026-11-04 (20 صورة إجمالاً).  
**المبدأ:** نستفيد من رحلات الاستخدام والأفكار، **ولا ننسخ التصميم أو العلامات أو نصوص المنافسين**. كل فكرة تُسند إلى وحدة قائمة أو تُسجّل للمستقبل، ولا نضيف صفحة/منتجاً جديداً بلا حاجة.

## 1. القرارات الثابتة

1. Beger هو **Smart Business OS** متعدد الفروع والمستأجرين، يبدأ بالمطاعم والمقاهي، ويمكن تفعيل وحدات بحسب نشاط المتجر. العيادات لها خصوصية وبيانات ومسارات عمل منفصلة.
2. لدينا **رحلتان** تعملان عبر نواة حالات/تنبيهات مشتركة:
   - **طلب إلكتروني:** QR طاولة/متجر → منيو → إضافات وسلة → إرسال → موافقة → تحضير → جاهز → تسليم → تقييم/أختام باختيار الزبون.
   - **Pager مستقل:** إنشاء رقم من الكاشير أو ربط مرجع فاتورة خارجية → بطاقة QR/رابط سري → متابعة → جاهز → تسليم، **بدون** إجبار المتجر على استخدام منيو Beger.
3. الزبون ليس مضطراً لإنشاء حساب أو تنزيل تطبيق. صفحة المتصفح تُظهر المتابعة. **Web Push / شاشة القفل / Wallet** قدرات منفصلة تحتاج دعم المتصفح والإذن، وليست مضمونة في جميع الأجهزة.
4. Beger يبيع **اشتراك البرامج**؛ لا يتوسط في مدفوعات الزبون أو التسويات. حالة «محصّل» تسجيل يدوي من التاجر، وليست إثبات دفع بنكي أو فاتورة ضريبية.
5. واجهة بسيطة: **صفحة/مساحة عمل واحدة لكل مهمة، تبويبات وفلاتر وعرض مضغوط افتراضي**. لا تجمع السجل والطلبات وكل الأدوات أسفل بعضها.
6. العربية/التركية/الإنجليزية، RTL صحيح، ثيمات فاتحة، ومعالجة جوال أولاً. الفروع معزولة بصلاحيات وتفعيل ميزات مستقل.
7. حماية النسخة العاملة: لا تعديل Production، ولا حذف بيانات، ولا ترقية شاملة دون اختبار على Staging ثم قبول المستخدم.

## 2. خلاصة الأفكار المصنفة من الصور

| لوحة تشغيل الكاشير بأرقام انتظار كبيرة | إصدار نداء سريع للمطاعم والأعمال التي تملك POS آخر | Pager مستقل | **الأولوية 1** |
| إنشاء رقم تلقائي أو إدخال رقم فاتورة خارجي | لا يلزم منيو Beger | مرجع خارجي منفصل عن معرف الطلب | **الأولوية 1** |

| تحليلات ساعة الذروة ومتوسط الانتظار | قرارات تشغيلية | طوابع حالات حقيقية | **مرحلة 2** |
| رضا الزبائن وتوزيع النجوم | تقييم جودة الخدمة | تقييمات مرتبطة بطلبات مكتملة | **موجود تجريبياً؛ تعميم لاحق** |
| رسائل جماعية للعروض | عودة العملاء | اشتراك صريح + إلغاء الاشتراك + حد تكرار | **مرحلة 3؛ لا بث بلا موافقة** |
| إشعارات متكررة للنداء | تقليل الطلبات غير المستلمة | حدود معدل الإشعار ومنع الإزعاج | **مرحلة 2** |
| بطاقة انتظار بصرية مخصصة للعلامة | دعم العلامة والتميّز | ثيمات المشروع القائمة | **تحسين تصميم تدريجي** |
| لوحة متاجر/فروع موحدة HQ | إدارة متعددة الفروع | عزل المستأجر والفرع | **موجود جزئياً** |
| وظائف الولاء في نهاية الرحلة | زيادة الاحتفاظ بالزبائن | ختم اختياري بعد التسليم | **تجريبي ومغلق افتراضياً** |

> **المراجع البصرية ليست دليل تنفيذ**: ما يُرى في الصور لا يعني أن ميزات مثل Push/Wallet/الوقت التقديري تعمل بالفعل عند المنافس أو داخل Beger.

## 3. تصميم المنتج بلا زحمة

### مساحات التاجر، ثابتة وقابلة للتفعيل بحسب النشاط

- **نظرة عامة:** المؤشرات الأساسية فقط، مع روابط إلى التفاصيل.
- **الطلبات والمطبخ:** رحلة طلبات Beger؛ حيّة / سجل / فلاتر / طباعة.
- **البيجر والنداء (وحدة مستقلة):** كاشير إنشاء نداء، شاشة انتظار داخلية، QR للنداء، حالات وتسليم. **لا يظهر للمحل إذا لم يفعّل الوحدة**.
- **الكتالوج والقائمة:** المنتجات والتصنيفات والإضافات والأسعار.
- **العملاء والتسويق:** تبويبات منفصلة للتقييمات والولاء والعروض والرسائل، ولا نضيف وحدات إلى القائمة الرئيسية لمجرد ظهورها في صورة.
- **التقارير:** مؤشرات من أحداث حقيقية، مع فصل الإيراد المسجل عن التحصيل.
- **الفروع وQR والإعدادات:** إدارة الأجهزة/الروابط واللغات والثيمات والأدوار.

### الواجهات المطلوبة داخل Pager فقط

1. **Cashier** — إجراء رئيسي واحد: «رقم انتظار جديد»؛ رقم واضح، مرجع فاتورة اختياري، زر عرض/طباعة QR.
2. **Live Board** — حالات انتظار/قيد التحضير/جاهز؛ أزرار قليلة، بحث سريع؛ دعم وضع ملء الشاشة للأرقام دون بيانات شخصية.
3. **Customer Ticket** — رقم نداء كبير، حالة، تعليمات الاستلام، إعدادات تنبيه؛ لا منيو مفروض على مستخدم البيجر فقط.
4. **Analytics** — تبويب وليس صفحة تملأ شاشة الكاشير، مع أرقام مبنية على حالات فعلية.

## 4. نموذج البيانات وحدود الأمان المقترحة

**لا تخلط رقم النداء المرئي مع المعرف السري**. نحتاج كياناً مستقلاً للنداءات غير المرتبطة بطلب Beger، ولا نستعمل مباشرة بيانات طلبات المنيو:
- `pager_tickets`: `id`, `business_id`, `branch_id`, `display_number`, `external_receipt_ref?`, `status`, `created_at`, `ready_at?`, `fulfilled_at?`, `created_by`, و**رمز وصول سري منفصل**.
- `pager_events`: انتقالات الحالة والسجل والزمن والموظف؛ لا يُسمح بحذف تاريخ التشغيل من واجهة الزبون.
- `pager_settings`: تمكين الوحدة، أنماط الترقيم، قنوات التنبيه، إعدادات العرض/الطباعة، لكل فرع.
- ربط اختياري ب`g3_orders` عند وجود طلب منيو، لكن Pager مستقل **لا يخلق طلباً مالياً مزيفاً**.

**قيود إلزامية:** RLS وعزل الفرع؛ الموظف لا يعدّل فرعاً آخر؛ النداء العام لا يكشف أرقام هواتف أو أسماء؛ رقم ظاهر غير كافٍ وحده لفتح تفاصيل الطلب؛ حالة التسليم تمنع إعادة النداء المتكرر؛ مقاومة التكرار والتسابق في إصدار أرقام اليوم؛ قيود معدل الطلبات وتجربة فتح الرابط على جهاز آخر.

**إشعارات/تسويق:** إذن صريح ومحدد القناة، إلغاء سهل، حدود إرسال، لا اعتبار المتصفح المغلق مغطى دون Push مُختبر. لا طلب للوصول إلى جهات اتصال أو ملفات الهاتف.

## 5. ترتيب التنفيذ والقبول

### P0 — لا نكسر الموجود
- الحفاظ على رحلات المنيو والطاولة والسفري والتسليم والتنبيهات والتقييمات/الأختام الموجودة.
- اختبار `npm test`، `npm run build`، RLS وسيناريو زبون/تاجر/مطبخ على Staging.
- الحفاظ على رابط معاينة واحد وعدم لمس Production.

### P1 — Pager مستقل: نسخة تجريبية قابلة للاختبار
- قاعدة بيانات ورقم انتظار ذري مع رمز متابعة غير قابل للتخمين.
- لوحة الكاشير: إصدار/بحث/تغيير حالة/إلغاء/تسليم.
- QR/رابط متابعة فريد + بطاقة من صفحة واحدة + طباعة بسيطة.
- اختبار: مسح QR، متابعة زبون على جهاز ثانٍ، تحديث حالة آني/استطلاع احتياطي، عدم كشف غير المصرح لهم، وعدم مضاعفة النداء.
- نجاحها لا يتطلب تشغيل الكتالوج أو جمع الأموال.

### P2 — تحسين الخدمة في المطعم
- شاشة الأرقام العامة، إدارة محطات الطباعة، متوسط انتظار مبني على أحداث حقيقية، خيارات تكرار النداء.
- تحذير واضح عند غياب Push أو عدم دعم الصوت في الخلفية.
- UX للوصول السريع، أقل عدد نقرات، أزرار لمس كبيرة.

### P3 — نمو وتسويق ضمن الموافقات
- رسائل جماعية لمن اشترك اختيارياً فقط مع إلغاء الاشتراك وسجل تسليم وحماية من الإرسال المتكرر.
- تحسين الولاء والاستبدال بعد بناء قواعد صرف محمية، ثم تكاملات Wallet إن ثبتت الحاجة.
- تقارير الأداء المتقدمة وتخصيص العلامة لكل فرع.

## 6. ما لا نبنيه الآن

- تطبيق هاتف مستقل لمجرد الإشعارات، أو نظام مدفوعات وتسويات خاص بنا.
- خصومات تلقائية من الأختام التجريبية، أو أرقام انتظار غير محمية برمز متابعة.
- رسائل تسويقية للمستخدمين بلا موافقة، أو ادعاء Push عند إغلاق المتصفح قبل اختبارها.
- عشرات صفحات/بطاقات جديدة وميزات مبنية لمجرد تقليد مظهر الصور.
- حسابات زمن انتظار مزيفة أو مواعيد تسليم مضمونة.

## 7. متابعة التنفيذ

أي مهمة جديدة مرتبطة بالصور تُسجَّل تحت **وحدة واحدة موجودة**، مع: **حالة** (`idea / scoped / in-progress / staging / validated / production-approved`)، **اختبار قبول**، **اعتماديات**، و**قرار عدم التكرار**. هذه الوثيقة هي **مصدر قرارات مرجعي** للأفكار المستخلصة من الصور، وليست سجل إصدار ولا شهادة بأن ما فيها منفذ.

**نقطة البدء التالية:** تطبيق **P1 Pager مستقل** بوحدة محمية وقابلة للتفعيل، دون إدخالها في مسار طلبات المنيو قبل اجتياز الاختبارات.
